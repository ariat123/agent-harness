# Maps Lead Research

Use the canonical repository at the `maps-lead-research/` folder in this repository and its `.venv/bin/python -m maps_lead_research` CLI. If it has moved, locate the installed package/repository before continuing. Read its `README.md`, `docs/campaign-defaults-v2.json`, and `docs/architecture.md` as needed for inputs, budget semantics, and recovery. Do not recreate scraping, geography expansion, deduplication, extraction, receipts, or exports in the prompt or skill.

By default, a request to find companies means the full discovery-and-research workflow (`run`): discover net-new companies, research their public websites, find decision makers and work-email candidates where supported, and export results and gaps within the agreed limits. The user does not need to append "research their decision makers" or "find their emails". Use discovery alone only when the user requests company listings without enrichment; use enrichment alone for existing companies. Missing contacts or emails remain explicit gaps, never invented results.

Translate a natural-language request into a version 2 campaign JSON. Ask only for materially missing inputs: company type, geography, maximum net-new companies, minimum reviews, maximum contacts/emails, and Firecrawl permitted account-credit delta. Use the established shared registry, a unique output directory, explicit Maps request ceiling, Firecrawl reserve, and page limits. Propose conservative defaults when absent: two contacts/emails, two Firecrawl operations and one HTTP page per domain. A zero Firecrawl delta disables paid research. Keep category/source relevance separate from downstream ICP qualification; do not add size, ownership, assumed need, buying signals, or offer-fit gates.

Run `plan` once offline (it also validates the configuration) and present the concrete target and hard provider limits. Use standalone `validate` only when a plan is not needed. `keys` reports key presence only; never read or print `.env`, keys, provider headers, or raw exception bodies. Import known historical files with `import-history` when they are not yet represented; inspect import/quarantine counts instead of assuming every CSV is authoritative.

**Require explicit authorization before paid provider execution.** A request to prepare a campaign, a positive budget in a file, or a request for a plan is not by itself approval to spend. Once the user explicitly approves executing the presented campaign within its hard limits, use `--allow-paid` without asking again for that same authorized scope. Add `--allow-http` for the agreed lightweight website research. Use `balance --live` only when a live account-balance check is requested or part of approved execution. Do not run a verifier or outreach operation.

For routine campaigns, keep Codex supervision minimal: prepare the configuration, launch one `run` command with the authorized flags, wait for that process, and summarize its final results. Python owns Maps queries/pagination, shared-registry deduplication, website selection, HTTP/Firecrawl requests, contact/email extraction, retries, receipts, CSV generation and validation. Do not split the campaign into per-company tool calls, manually browse or reason over each company, rewrite scripts, re-audit the repository, or re-import represented history during an ordinary run. Use the existing process session to wait, with up to 60-second waits and brief required progress updates; do not repeatedly read CSVs or raw pages while it is healthy. Diagnose only concrete errors, invalid outputs or unexplained shortfalls. Contact/email gaps alone do not authorize manual research beyond the configured workflow. Read detailed evidence only for a specific issue or an explicit research request.

Live provider commands need network access. In a network-restricted sandbox, use the execution tool's network-capable approval path for the already-authorized command; do not run a campaign repeatedly inside the blocked sandbox. A DNS preflight failure occurs before any Maps request and does not require a new campaign budget. For preserved pending requests, keep their accounting intact and distinguish local attempts from confirmed provider billing. Diagnose network access before proposing further paid attempts. When the user explicitly authorizes a concrete bounded verification request, execute it without asking for the same authorization again.

Invoke `discover`, `enrich`, `run`, or `batch` for the requested scope. `enrich --backlog` resumes previously discovered incomplete companies without new Maps searches. Use `status` only when progress is requested or a suspected problem needs diagnosis; resume using `resume RUN --stage ...` and the same authorized limits. Never erase pending receipts, reset budget counters, or substitute a legacy script to bypass a stopping condition. Unknown provider outcomes require preserved evidence/reconciliation; budget exhaustion stays in the backlog. Increasing limits or refreshing successfully researched domains requires explicit authorization for that additional spending and a new campaign/run configuration.

Execution already exports CSVs and runs validation. Inspect the returned validation summary and `run_summary.md` once before handoff; read `validation_report.json` for additional detail when needed. Run standalone `export` only to regenerate missing/stale outputs after a relevant state change, not after every successful execution. Use `rebuild RUN --output NEW_DIRECTORY` for offline reconstruction. Return links to `companies.csv`, `people_contacts.csv`, `email_candidates.csv`, `research_gaps.csv`, `firecrawl_backlog.csv`, and `run_summary.md` as relevant. Report net-new companies separately from resumed historical backlog, actual provider attempts/balance delta, unresolved gaps, and shortfalls. Public emails are source-backed, inferred emails are candidates, and both remain mailbox-unverified.
